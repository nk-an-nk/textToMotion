# 一文一モーションと継続会話

## 一文ごとの出力

0.5系のAndroidアプリは、バックエンドへ `sentence_plan: true` を送ります。
LLMは1回の要求で、1〜6文・合計400字以内の返答と、文ごとの動作を作成します。
①では各文のmotion_id、②では各文のgestureカテゴリを返します。文ごとに追加のLLM呼出は行いません。

```json
{
  "sentences": [
    {"speech": "こんにちは！", "gesture": "greet", "motion_id": null},
    {"speech": "何をして遊びたい？", "gesture": "question", "motion_id": null}
  ],
  "language": "ja",
  "timing": "speech_start"
}
```

上記はカテゴリ方式のモデル出力です。APIは従来の `speech/gesture/language/timing` も集約して返すため、本文は画面でまとめて確認できます。
`sentence_plan` がない旧クライアントへの平坦な応答も維持します。
日本語の。！？と英語の終止符を補助的に分割し、1つの配列要素へ複数文が入った場合も文単位に分けます。小数点は分割しません。
候補がある文は1つの動作を選び、候補外ID・利用できない動作は実行しません。

同じ返答の中で同じ動作が再選択された場合は、一文一動作を優先して再生できます。
別の会話ターンへのクールダウンは維持します。カテゴリ方式では可能な限り未使用/再生が古い候補を選びます。

## 発声と動作のタイミング

0.5.0ではTTS開始通知から動作を要求しましたが、実機では動作の開始が132〜2,382ms遅れる例がありました。
0.5.1では順序を次のように変更しています。

1. その文の動作を選び、再生を要求する。
2. SDKの動作開始通知を受ける。
3. 直ちにその文のTTSを要求する。
4. 文のTTS完了で長い動作を停止し、次の文へ進む。

動作の準備に時間がかかる場合は、声だけを先行させず、発声を待たせます。
動作開始通知が8秒来ない場合は停止してエラーを表示します。動作エラー時は記録して音声だけを継続できるようにしています。
これはSDK通知に合わせる制御で、音響的な開始と機械の動きが物理的に完全一致するという保証ではありません。

文間では古いSDK通知が次の文へ混ざらないよう、出力を停止してSDK接続を更新します。
次の文は接続完了後の80ms待機を経て開始します。接続・動作の準備に伴う文間の間隔は残ります。
各文に操作トークンを付け、前の文の完了通知、重複通知、停止後の通知を除外します。

## 継続会話

「会話を開始（返答後も自動で聞き取り）」を1回押すと、
`音声認識 → LLM → 文ごとの発声・動作 → 次の音声認識` を繰り返します。
次の発話ごとにボタンを押す必要はありません。返答中は認識を停止し、自分の声を認識しないようにします。
SDKが再接続し、返答終了後の700ms待機を経て次の認識を始めます。状態がLISTENINGになったら話しかけてください。

同じセッションIDで直近6往復をバックエンドへ引き継ぎます。
「会話を終了 / 停止」で、認識・出力・自動再開予約を取り消します。
無言タイムアウトや空の認識結果は再度待ち受けます。認識エラーが3回続く場合やSDK/バックエンドの異常では停止して原因を表示します。
「新しい会話」、言語や実験条件の変更、画面を離れた場合は履歴を切り替え/破棄します。
言語や実験条件を変えるときは、先に会話を終了してください。

## 記録

同じ返答の `conversation_id` に `sentence_index/sentence_count` を付けて文を区別します。
`sentence_start`、`motion_request/start_notification`、`tts_request/start_notification/complete`、`sentence_complete` と `sentence_metrics` を記録します。
`sentence_metrics.start_difference_ms` は「動作開始通知 − TTS開始通知」で、負値なら動作通知が先です。

速度履歴とCSVには文数・実際に要求した動作IDの列を追加しています。本文は既定では保存しません。
過去の速度比較は0.4系の返答全体に1動作の契約による結果です。文単位の新形式と、そのまま同条件の結果として混ぜないでください。

## 0.6の会話速度優先方式

0.5.1の「動作の開始通知まで声を待つ」方式はずれを小さくできますが、文の間が長くなりました。
0.6では日常会話の自然さを優先し、SDKのmotionPrepareで読み込んでから、準備済みmotionPlay()とTTSを続けて要求します。
文ごとのSDK接続し直しを省き、音声通知の世代番号を更新して古い文の通知を除外します。文間の固定待機も80msから10msへ減らします。
動作の事前読み込みが1.8秒以内に完了しない場合はその動作を停止し、エラーを記録して音声だけを継続します。
停止/画面終了では予約と準備中の処理を取り消し、通常どおりSDKを終了・再接続します。
初回の速度確認では返答を原則1〜2文とする推奨を入れましたが、2026-10-29に日本語学習への影響を調べるため、この推奨だけを試験的に外しました。最大6文・合計400字、一文一動作、短く年齢に適した文を使う指示は維持します。正式採用は会話品質の確認後に判断します。[文数条件の予備比較](response-length-trial.md)を参照してください。

仕様：[メーカーAPIのmotionPrepare/motionPlay](https://developer-docs.nuwarobotics.com/sdk/javadoc/reference/com/nuwarobotics/service/agent/NuwaRobotAPI.html#motionPrepare(java.lang.String))。

0.6の実機2応答では文間119〜189ms、SDKの動作開始通知−TTS開始通知は−10〜0msとなり、利用者から自然さの改善を確認しました。[詳細記録](device-verification.md)。

## 0.7の返答生成モデル比較

画面で返答生成モデルを指定する新方式では、文章生成と動作選択を2回のAPI呼び出しに分けます。選択したモデルが文章だけを生成し、固定モデルが各文の動作をまとめて選択します。旧クライアントの一括生成は継続します。[モデル比較](model-comparison.md)を参照してください。

## 0.8のカテゴリ内ID選択

0.8.0のカテゴリ方式（従来7種・拡張25種）は、文章生成、カテゴリ選択、カテゴリ内の動作ID選択の3段階です。
文章生成には画面で指定したモデルを使用し、後半2段階はバックエンドの固定モデル（現行設定はGPT-4.1 mini）を使用します。
各段階は返答の全文章を一括処理します。文章ごとにAPIを再呼出しする方式ではありません。

Kebbiからは利用可能なID・説明・カテゴリの対応を渡します。有効・無効、7種/25種、クールダウンを反映します。
カテゴリをLLMが選んだ後、そのカテゴリに属する候補だけを別のLLM要求へ渡して動作IDを選びます。
IDの写し間違いや別文のカテゴリからの選択を防ぐため、LLMは文ごとの候補番号を返し、サーバーはその候補の正確なIDを返します。
これはLLMが選んだ候補の参照であり、端末ルールによる再選択ではありません。
カテゴリ外・未登録のIDはバックエンドでエラーにします。Kebbiでも候補所属・現在の対応表・利用可能性を再検証します。
LLMがnullを返した場合はその文を音声のみで出力し、端末ルールで別のIDを補いません。
文ごとのmotionPrepare・TTSと動作の同時要求・継続会話の制御は維持します。

画面・履歴・CSVに `category_selection_ms`（カテゴリ選択）、`id_selection_ms`（ID選択）、
`motion_selection_ms`（両段階の合計）を保存します。各時間はAPI通信と応答検証を含みます。
`motion_id_selection` で旧方式（rule）と新方式（llm）を区別し、異なる方式の平均を混ぜません。
①全ID直接選択は引き続き1回の選択要求でIDを決めます。

新APKは `category_motion_selection=llm` を送ります。旧クライアントや比較試験のrule指定では旧方式を維持します。
実機用APKはGitHub Actionsでビルドし、PCだけの速度比較は次で再現できます。

```bash
PYTHONPATH=kebbi-conversation/backend python kebbi-conversation/scripts/benchmark-category-ids.py \
  --catalog /path/to/motion-mapping.json --output /path/to/results
```

キーは環境変数 `LLM_API_KEY`、または `--api-key-file` で指定します。キーを結果ファイルへ保存しません。
同じ5文×5セットを各条件3反復し、GPT-4.1 miniで旧カテゴリ選択と新カテゴリ→ID選択を比較します。
各条件1回のウォームアップは除外し、成功・失敗件数、段階別時間、5文一括の平均・中央値、1文換算を記録します。
返答文生成・ASR・TTS・実機出力・旧方式の端末内ID選択時間はこのAPI試験に含みません。
